1 Objet & périmètre

Ce plan décrit les mesures de sauvegarde, de continuité et de reprise du Hub Astorya en cas d'incident majeur (indisponibilité, corruption, compromission, sinistre). Il couvre l'application (front statique + fonctions serverless, Vercel), la base de données (Supabase/PostgreSQL), le code source (GitHub) et la chaîne de déploiement, les secrets & configurations, les services tiers (Pappers, Dropcontact, Brave, SendGrid, Google Calendar, 3CX, IA) et la téléphonie 3CX.

Hors périmètre : postes de travail individuels, réseau local du client, opérateurs télécom.

5 Dispositif de sauvegarde

  • Base de données : sauvegardes automatiques Supabase avec restauration point-in-time (PITR) ; export logique régulier (pg_dump) stocké hors-ligne / hors-site (règle 3-2-1, conforme ANSSI).
  • Code source : GitHub = source de vérité (historique complet, branches protégées) ; front pré-compilé (dist/) versionné → reconstruction sans dépendance externe.
  • Secrets : gestionnaire de mots de passe / coffre-fort + variables d'environnement Vercel ; liste des variables maintenue.
  • Documents comptables : exports FEC et pièces archivés (conformité DGFiP).
  • Infrastructure : vercel.json, scripts, mappings — versionnés dans Git.

6 Scénarios de sinistre & procédures

S1 — Indisponibilité de l'hébergeur edge (Vercel)RTO ≤ 1 h

Impact : application inaccessible.

Reprise : vérifier l'état Vercel → si panne prolongée, redéployer le dépôt Git sur une instance de secours (nouveau projet Vercel ou serveur OVH) → repointer le DNS.

S2 — Indisponibilité / corruption de la base (Supabase)RTO ≤ 4 h · RPO ≤ 5 min

Reprise : PITR vers l'instant précédant l'incident → si projet perdu, recréer un projet Supabase et restaurer l'export logique → mettre à jour SUPABASE_URL/clés.

S3 — Rançongiciel / compromission de donnéesRTO ≤ 8 h · RPO ≤ 24 h

Reprise : isoler (révoquer clés & sessions, couper les accès) → restaurer depuis la copie hors-ligne (non chiffrable par l'attaquant) → rotation complète des secrets → analyse post-incident.

La copie hors-ligne 3-2-1 est la garantie clé.

S4 — Perte / fuite de secretsRTO ≤ 1 h

Reprise : rotation immédiate des clés (Supabase service_role, Pappers, Dropcontact, Brave, SendGrid, Google SA, secret 3CX) → mise à jour des variables d'env → redéploiement.

S5 — Panne DNS / domaineRTO ≤ 2 h

Reprise : vérifier la zone chez le registrar → recréer les A/CNAME vers l'edge → propagation (TTL). Prévoir un TTL court avant toute opération planifiée.

S6 — Indisponibilité de GitHubRTO ≤ 4 h

Impact : déploiements bloqués (service en ligne non impacté).

Reprise : utiliser un miroir / clone local à jour ; déployer manuellement si besoin.

S7 — Panne de téléphonie (3CX)RTO ≤ 4 h

Reprise : renvoi d'appel opérateur ; hotline en mode dégradé (e-mail/ticket) ; le webhook /api/3cx-webhook reprend au rétablissement.

S8 — Sinistre majeur → bascule serveur OVH dédié (cible)RTO ≤ 8 h · RPO ≤ 1 h

Reprise : déployer le dépôt sur le serveur OVH (France) → restaurer la base (PITR/export) → injecter les secrets → repointer le DNS → valider.

7 Procédure générale (synthèse)

  1. Qualifier l'incident (composant, gravité) et déclencher le PRA.
  2. Isoler si compromission (révocation clés/sessions).
  3. Restaurer la donnée (PITR ou export hors-ligne) sur l'infra saine.
  4. Redéployer l'application depuis Git.
  5. Réinjecter les secrets (rotation si nécessaire).
  6. Repointer le DNS vers l'infra de reprise.
  7. Vérifier les flux critiques (connexion, facturation, contrats, e-mail).
  8. Communiquer aux utilisateurs ; documenter (post-mortem).
